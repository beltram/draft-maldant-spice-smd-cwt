             Selective Disclosure CBOR Web Tokens (SD-CWT)
                   draft-maldant-spice-smd-cwt-latest

Abstract

   This document specifies an extension to Selective Disclosure CBOR Web
   Tokens (SD-CWT) that reduces their size and improves their privacy
   properties.  The individual hashes of redacted claims are replaced by
   the root of a single Merkle tree, and disclosed claims are presented
   with a Merkle proof.

1.  Introduction

   This document defines Selective Merkle Disclosure CBOR Web Tokens
   (SMD-CWT), an extension to SD-CWT [SD-CWT].

   SD-CWT provides an efficient mechanism for a Holder to control which
   claims it presents to a Verifier, thereby improving the Holder's
   privacy.  However, when only a subset of the claims is disclosed, the
   Verifier still learns the total number of claims, which reduces the
   privacy benefit of selective disclosure.  In addition, each redacted
   claim adds 34 bytes to the presented token (SD-KBT), even though it
   is not presented to the Verifier.

   To address both issues, this document specifies that, instead of
   hashing each claim individually and placing the hashes in a CBOR
   array, the claims are placed in a Merkle tree and only its root hash
   is included in the SD-CWT.  A presentation of the token then only
   needs to include a Merkle proof for the disclosed claims to attest to
   their integrity.  The size of this proof is logarithmic in the number
   of claims, whereas the size of an enumeration of all redacted claims
   is linear.

   This specification defines the following new terms:

   Selective Merkle Disclosure CBOR Web Token (SMD-CWT):  An SD-CWT with

   Selective Merkle Disclosure Key Binding Token (SMD-KBT):  An SD-KBT
      used to demonstrate possession of a confirmation method and to
      present claims with a Merkle proof.

   All other terms used in this document have the same meaning as in
   [SD-CWT].

3.  Overview

   SMD-CWT is an extension of SD-CWT: every SD-CWT is a valid SMD-CWT,
   but an SMD-CWT is not necessarily a valid SD-CWT.  The two differ
   only in how redacted claims are authenticated and presented.

   Whereas an SD-CWT Issuer enumerates all claim hashes in a CBOR array
   or map, an SMD-CWT Issuer places these hashes at the leaves of a
   left-balanced Merkle tree and replaces the set of claims in the
   original payload with the root hash of that tree.

   A Holder can then selectively present claims to a Verifier in an SMD-
   KBT by replacing the disclosed claims with proofs of their inclusion
   in the Merkle tree, whose root hash is authenticated by the Issuer in
   the SMD-CWT.

4.  Issuance

   An SMD-CWT Issuer is also an SD-CWT Issuer.  It MUST be capable of
   encoding and signing a regular SD-CWT when requested, and
   additionally supports generating SMD-CWTs.

   Figure 1 shows an example CWT payload.  Common claims are omitted for
   brevity.

   {
       "most_recent_inspection_passed": true,
       "inspector_license_number": "ABCD-123456",
       "inspection_dates" : [
           1549560720,   / 2019-02-07T17:32:00 /
           1612498440,   / 2021-02-04T20:14:00 /
           1674004740,   / 2023-01-17T17:19:00 /
       ],
       "inspection_location": {
           "country": "us",            / United States /
           "region": "ca",             / California /
           "postal_code": "94188"
       }
   }

4.1.  Pre issuance

   An SMD-CWT Issuer MUST support the To Be Redacted Tag defined in
   Section 17.3.1 of [SD-CWT] and the To Be Decoy Tag defined in
   Section 17.3.1 of [SD-CWT].

   To signal to the Issuer that a claim or array element is intended to
   be part of a Merkle Disclosure, this specification uses the To Be
   Redacted Root Tag defined in Section 8.1.1.

   Figure 2 shows the example payload annotated accordingly.

   59([3, { /merkle-redacted of size 8/
       "most_recent_inspection_passed": true, /not-redacted/
       "inspector_license_number": 58("ABCD-123456"), /redacted/
       59([3, "inspection_dates"]) : [ /merkle-redacted of size 8/
           58(1549560720), /redacted/
           1612498440,     /not-redacted/
           58(1674004740), /redacted/
       ],
       59([2, "inspection_location"]): { /merkle-redacted of size 4/
           "country": 58("us"),   /redacted/
           "region": 58("ca"),    /redacted/
           "postal_code": "94188" /not-redacted/
       }
   }])

                   Figure 2: CWT Claims Set Pre Issuance

   At each level where the To Be Redacted Root Tag is encountered, a
   Merkle tree is built and all inner elements are placed at its leaves.

4.2.  Merkle Tree

   This specification uses a left-balanced Merkle tree.

4.3.  Content-Type

   An SMD-CWT MUST declare its content type by including the typ
   protected header parameter [RFC9596] with one of the following
   values:

   *  the unsigned integer Constrained Application Protocol (CoAP)
      [RFC7252] content-format value TBD1 (294 suggested); or

   *  the string content type value application/smd-cwt+sd-cwt.

   IANA is requested to add the following entry to the "CBOR Tags"
   registry (https://www.iana.org/assignments/cbor-tags/cbor-
   tags.xhtml#tags):

8.1.1.  To Be Redacted Root Tag

   This tag identifies an array or map containing elements to be
   redacted.  The value of this tag is an array of two elements: the
   first is the logarithmic size of the desired proof length, and the
   second is the wrapped array or map.

   *  Tag: TBD2 (suggested 59)

   *  Data Item: (array or map)

   *  Semantics: An array or map containing elements to be redacted with
      a Merkle proof, each tagged with the To Be Redacted Tag defined in
      Section 17.3.1 of [SD-CWT].

   *  Specification Document(s): Section 4.1 of this specification

Appendix A.  Complete CDDL Schema

   ; in SMD-CWT
   salted-merkle-array = [ +bstr-encoded-merkle-salted ]
   bstr-encoded-merkle-salted = bstr .cbor salted-merkle-entry

   ; in SMD-KBT
   salted-array-proofs = [ +bstr-encoded-salted-proof ]
   bstr-encoded-salted-proof = bstr .cbor salted-merkle-proof

   ; where salted-claim, salted-element and decoy are already defined in {{SD-CWT}}
   salted-merkle-entry = salted-claim / salted-element / decoy / salted-merkle-leaves
   salted-merkle-proof = salted-claim / salted-element / decoy / salted-merkle-proof

   merkle-entry = salted-claim / salted-element / decoy
   salted-merkle-leaves = [ +merkle-entry ]

   salted-merkle-proof = [ +merkle-entry ]

   ; repeated here
   salted-claim = [
     bstr .size 16,     ; 128-bit salt
     any,               ; Claim Value
     (int / text)       ; Claim Key
   ]
   salted-element = [
     bstr .size 16,     ; 128-bit salt
     any                ; Claim Value
   ]
   decoy = [
     bstr .size 16      ; 128-bit salt
   ]

   ; redacted_claims_root is used as a map label. The corresponding value is
   ; a Redacted Claim Root Hash.
   ; TODO: any Unassigned value in https://www.iana.org/assignments/cbor-simple-values#simple
   redacted_claims_root = #7.60  ; CBOR simple value 60

   merkle_root_value = [
     bstr, ; root hash
     uint  ; logarithm(2) of the number of leaves represented in this root hash
   ]

   ; CBOR tag for wrapping the Merkle Root Hash of all the redacted elements in an array.
   ; TODO: any Unassigned in https://www.iana.org/assignments/cbor-tags#tags
   MERKLE_REDACTED_ELEMENT_TAGNUM = 89

   ; redacted_elements_root is used in CDDL payloads that contain
   ; array elements that are redacted.
   redacted_elements_root = #6.<MERKLE_REDACTED_ELEMENT_TAGNUM>( merkle_root_value )
