         Selective Merkle Disclosure CBOR Web Tokens (SMD-CWT)
                   draft-maldant-spice-smd-cwt-latest

Abstract

   This document specifies an extension to Selective Disclosure CBOR Web
   Tokens (SD-CWT) that reduces their size and improves their privacy
   properties.  In this extension, the individual hashes of the redacted
   claims of a map or an array are replaced with the root hash of a
   Merkle tree, and disclosed claims are presented with a Merkle proof.

1.  Introduction

   This document defines Selective Merkle Disclosure CBOR Web Tokens
   (SMD-CWT), an extension to SD-CWT [SD-CWT].

   SD-CWT provides an efficient mechanism by which a Holder controls
   which claims it presents to a Verifier, thereby improving the privacy
   of the Holder.  However, when the presentation is sparse and only a
   subset of the claims is disclosed, a Verifier learns the total number
   of claims, reducing the privacy benefit of selective disclosure.
   Furthermore, each redacted claim adds 34 bytes to the presented token
   (SD-KBT), even though the claim itself is not disclosed to the
   Verifier.

   To address both issues, this document specifies that, rather than
   hashing each claim individually and placing the resulting hashes in a
   CBOR array, the claims of each map or array are placed in a Merkle
   tree and only the root hash of that tree is included in the SD-CWT.
   A presentation of the token then includes only a Merkle proof
   attesting to the integrity of the disclosed claims.  The size of this
   proof is logarithmic in the number of claims, whereas the size of an
   enumeration of all redacted claims is linear in that number.

      on the path from that leaf to the root.

   [SD-CWT].

3.  Overview

   SMD-CWT is an extension of SD-CWT: every SD-CWT is a valid SMD-CWT,
   but an SMD-CWT is not necessarily a valid SD-CWT.  The two differ
   only in the way redacted claims are authenticated and presented.

   An SD-CWT Issuer enumerates the hashes of all redacted claims, either
   in the redacted_claim_keys array of a map, or in place of the
   redacted elements of an array.  In contrast, an SMD-CWT Issuer places
   these hashes at the leaves of a left-balanced Merkle tree and
   replaces the set of claims in the original payload with the root hash
   of that tree.

   A Holder then selectively presents claims to a Verifier in an SMD-KBT
   by replacing the disclosed claims with proofs of their inclusion in
   the Merkle tree.  The root hash of that tree is authenticated by the
   Issuer in the SMD-CWT.

4.  Issuance

   An SMD-CWT Issuer is also an SD-CWT Issuer: it MUST be capable of
   encoding and signing a regular SD-CWT when requested and, in
   addition, supports the generation of SMD-CWTs.

4.1.  Pre-Issuance

   An SMD-CWT Issuer MUST support the To Be Redacted Tag and the To Be
   Decoy Tag, both of which are defined in Section 17.3.1 of [SD-CWT].

   The To Be Redacted Root Tag (tag 59), defined in Section 10.1.1,
   indicates to the Issuer that a claim or an array element is intended
   to be selectively disclosed with a Disclosure Proof.  This tag wraps
   the element to be redacted in an array of size 2.  The first element
   of this array is the base-2 logarithm of the size of the Merkle tree
   used for redaction.  This size MAY be greater than the number of
   claims to redact, but MUST NOT be lower.

   Figure 2 shows the example payload with the corresponding
   annotations.

   59([3, { /merkle-redacted of size 8/
       "most_recent_inspection_passed": true, /not-redacted/
       "inspector_license_number": 58("ABCD-123456"), /redacted/
       59([3, "inspection_dates"]) : [ /merkle-redacted of size 8/
           58(1549560720), /redacted/
           58(1612498440), /redacted/
           58(1674004740), /redacted/
       ],
       59([2, "inspection_location"]): { /merkle-redacted of size 4/
           "country": 58("us"),   /redacted/
           "region": 58("ca"),    /redacted/
           "postal_code": "94188" /not-redacted/
       }
   }])

                  Figure 2: CWT Claims Set Before Issuance

   For each occurrence of the To Be Redacted Root Tag, at any nesting
   level, a Merkle tree is built, and all elements of the tagged array
   or map are placed at its leaves.

4.2.  Merkle Tree

   This specification uses binary Merkle trees similar to those defined
   in Section 2.1.1 of [RFC9162], with one difference: no domain
   separation prefix is added to the leaves and the nodes (see
   Section 4.3).  A higher branching factor would provide neither
   additional benefit nor the desired properties.

   The Merkle tree is a left-balanced perfect binary tree, as shown in
   Figure 3.  Unbalanced trees are not used, as they are vulnerable to
   forgery attacks.  Perfect binary trees are also easier to represent
   in memory, and their node indexes are easier to compute, as explained
   in Appendix C of [RFC9420].

                  |
              .---+---.
             /         \
      h(h(A)||h(B))    h(h(C)||h(d))
           / \         / \
          /   \       /   \
       h(A)   h(B)  h(C)  h(d)
         |     |     |     |
         |     |     |     |
         A     B     C    d

   Node: 0  1  2  3  4  5  6

   Leaf: 0     1     2     3

                      Figure 3: A 3-Claim Merkle Tree

   In Figure 2, the redaction of the "inspection_location" claim places
   the "country" claim at node index 0 and the "region" claim at node
   index 2.  Since a size of 2 is requested, the tree has a height of 2
   and its last node index is 6, as in Figure 3.

4.2.1.  Decoys

   Decoys serve a different purpose than in SD-CWT: they do not directly
   hinder the Verifier's inference of private information.  Instead,
   they act as a blinding factor that prevents a Verifier from inferring
   the number of leaves, since the hash of a blank leaf is the hash of
   zero bytes.  Decoys are therefore mandatory.

   Replacing every blank leaf with a Decoy would needlessly inflate the
   SMD-CWT.  Instead, for each node in the Copath of the rightmost
   entry, the leftmost blank leaf of the subtree rooted at that node
   MUST be replaced with a Decoy.  When the entries fill all the leaves
   of the tree, no Decoy is added.

   In Figure 4, the tree contains 9 entries.  Decoys (d) are placed as
   follows:

   1.  The rightmost entry of the tree is I.

   3.  For each node in this copath, the leftmost blank leaf of its
       subtree is replaced with a Decoy.  A blank copath node that is
       itself a leaf, such as 18, is replaced directly.

   4.  Consequently, nodes 18, 20, and 24 are replaced with Decoys.

4.3.  Computing the Merkle Root Hash

   The Issuer then computes the root hash of the Merkle tree as follows:

   1.  Each entry is encoded as a bstr-encoded-salted-merkle-entry, as
       defined in Figure 9.

   2.  The resulting bytes are hashed using the hash algorithm indicated
       by sd_alg in the protected header.

   3.  The hash of a parent node is the hash of the concatenation of the
       hashes of its two children, the hash of the left child coming
       first.

   This operation is denoted MTH (Merkle Tree Hash), similarly to the
   one described in Section 2.1.1 of [RFC9162].  Unlike in [RFC9162], no
   domain separation prefix is added to the leaves and the nodes: since
   the tree is balanced and its size is authenticated by the Issuer, all
   leaves are at the same depth.  The MTH of an interior node therefore
   cannot be used as the hash of a leaf, and second preimage resistance
   between leaves and nodes is not required.

4.3.1.  Inserting the Merkle Root Hash in the Payload

   The root hash is then inserted into the original payload in place of
   the redacted claims.  These claims are declared within a container,
   which is either a map or an array.  Since the container itself is
   annotated with the To Be Redacted Root Tag, it cannot contain regular
   redacted_claim_keys (simple value 59) or redacted array elements (tag
   60).

   Regardless of the type of the parent container, the root hash is
   represented as a redacted_root_hash: an array of two elements, the
   first of which is the logarithmic size of the Merkle tree producing
   the root hash, and the second of which is the root hash itself.

   redacted_root_hash = [
     uint,  ; base-2 logarithm of the number of leaves represented in this root hash
     bstr, ; root hash
   ]

                        Figure 5: Redacted Root Hash

   If the redaction occurs in a map, the redacted_root_hash is placed in
   the redacted_claim_hash claim.

   / redacted_claim_hash / simple(60) : [ uint, bstr ] / redacted_root_hash /

                       Figure 6: Redacted Claim Hash

   If the redaction occurs in an array, the root hash is placed in an
   redacted_element_hash element appended to the array, after the
   elements that are not redacted.

   "inspection_dates" : [
       1612498440, / item 1 not redacted /
       89([ uint, bstr ]) / root hash of item 0 and 2 /
   ],

                      Figure 7: Redacted Element Hash

   In an SMD-CWT, a Disclosure is an array of all redacted elements of a
   given container (either a CBOR map or array).  Each of these elements
   has the structure described in Section 3.2 of [SD-CWT], except that
   they are not individually wrapped in a CBOR bstr (but the outer
   disclosure is).

   This Disclosure, along with all other Disclosures, MUST be placed in
   the sd_claims unprotected header parameter of the SMD-CWT, as defined
   in [SD-CWT].

   ; an array of bstr-encoded Salted Disclosed Claims
   ; in SMD-CWT
   salted-merkle-array = [ +bstr-encoded-salted-merkle-entry ]
   bstr-encoded-salted-merkle-entry = bstr .cbor salted-merkle-entries

   ; in SMD-KBT
   salted-array-proofs = [ +bstr-encoded-salted-proof ]
   bstr-encoded-salted-proof = bstr .cbor disclosure-proof

   ; where salted-claim, salted-element and decoy are already defined in {{SD-CWT}}
   salted-merkle-entry = salted-claim / salted-element / decoy

   salted-merkle-entries = [ +salted-merkle-entry ]

   ; one Merkle proof per presented leaf, ordered by increasing node index
   disclosure-proof = [ +merkle-proof ]

   merkle-proof = [
     redacted-entry,
     * bstr             ; hash of a copath node, from the leaf up to the root
   ]

   ; a presented entry prefixed with the node index of its leaf; Decoys are never presented
   redacted-entry = salted-merkle-claim / salted-merkle-element
   salted-merkle-claim = [
     uint,              ; node index of the leaf
     bstr .size 16,     ; 128-bit salt
     any,               ; Claim Value
     (int / text)       ; Claim Key
   ]
   salted-merkle-element = [
     uint,              ; node index of the leaf
     bstr .size 16,     ; 128-bit salt
     any                ; Claim Value
   ]

   ; repeated here
   salted-claim = [
     bstr .size 16,     ; 128-bit salt
     any,               ; Claim Value
     (int / text)       ; Claim Key
   ]
   salted-element = [
     bstr .size 16,     ; 128-bit salt
     any                ; Claim Value
   ]
   decoy = [
     bstr .size 16      ; 128-bit salt
   ]

4.5.  Content-Type

   An SMD-CWT MUST declare its content type by including the typ
   protected header parameter [RFC9596] with one of the following
   values:

   *  the unsigned integer Constrained Application Protocol (CoAP)
      [RFC7252] content-format value TBD1 (294 suggested); or

   *  the string content type value application/smd-cwt+sd-cwt.

5.  Presentation

   A Holder can selectively present some of the previously redacted
   claims in an SMD-KBT.  An SMD-KBT has the same structure as an SD-
   KBT.  The only difference is that, rather than simply omitting the
   Disclosures it does not wish to reveal, the Holder transforms each
   Disclosure introduced by this document from a simple enumeration of
   values into a Disclosure Proof: an array containing one Merkle proof
   per presented leaf.

   The Merkle proofs of a Disclosure Proof are not independent of each
   other.  The hash of a copath node is not included in a Merkle proof
   when its subtree contains a presented leaf, since the Verifier
   recomputes it, or when it is already included in the Merkle proof of
   a previous leaf.

   For a given Disclosure, the Holder proceeds as follows:

   1.  Iterate over the non-Decoy entries and select those to be
       presented.  In the example of Figure 11, leaves A to E are
       iterated over, and only A, D, and E are presented.

   2.  Initialize a visited set with the node indexes of the selected
       leaves and of all their ancestors.  In the example of Figure 11,
       the visited set contains nodes 0, 6, and 8 (A, D, and E) and
       nodes 1, 3, 5, 7, 9, and 11 (J, R, K, V, L, and S).

   3.  For each selected leaf, from left to right, build its Merkle
       proof as an array:

       1.  Build a Redacted Entry by prefixing the SMD-CWT entry with
           the node index of the leaf, and place it as the first element
           of the Merkle proof.

       2.  Walk the copath of that leaf, from the leaf up to the root.
           For each node of the copath:

           1.  If this node is in the visited set, skip it.

           2.  Otherwise, append the hash of that node to the Merkle
               proof and add the node to the visited set.  If that node
               is a leaf, its hash is the hash of its entry, computed as
               described in Section 4.3.  Otherwise, its hash is the MTH
               of the subtree rooted at that node.

   4.  The Disclosure Proof is the array of the Merkle proofs, ordered
       by increasing node index of their leaf.

                  Figure 11: Merkle Tree of a Presentation

   In the following examples, hash<<X>> denotes the hash of the entry X
   when X is a leaf, and the MTH of the subtree rooted at X otherwise.

   The copath of A consists of nodes 2 (B), 5 (K), and 11 (S).  B is not
   visited: its hash is appended.  K and S are visited: they are
   skipped.  The Merkle proof for A is therefore:

   [
     [0, h'4e2f040d5bb57daf86698066be470c24', "A"],
     hash<<B>>,
   ]

                        Figure 12: Merkle Proof of A

   The copath of D consists of nodes 4 (C), 1 (J), and 11 (S).  C is not
   visited: its hash is appended.  J and S are visited: they are
   skipped.  The Merkle proof for D is therefore:

   [
     [6, h'add7fe2b052af5faf0ec67f57eb1454f', "D"],
     hash<<C>>,
   ]

                        Figure 13: Merkle Proof of D

   The copath of E consists of nodes 10 (d1), 13 (M), and 3 (R). d1 and
   M are not visited: their hashes are appended.  R is visited: it is
   skipped.  The Merkle proof for E is therefore:

   [
     [8, h'6e0e0494c6aa9f9072c3410304aab730', "E"],
     hash<<d1>>,
     hash<<M>>,
   ]

                        Figure 14: Merkle Proof of E

   The resulting Disclosure Proof is shown in Figure 15.  It contains 4
   hashes.  The hashes of J, K, R, L, S, and V are recomputed by the
   Verifier.

   [
     [ [0, h'4e2f040d5bb57daf86698066be470c24', "A"], hash<<B>> ],             / "A" /
     [ [6, h'add7fe2b052af5faf0ec67f57eb1454f', "D"], hash<<C>> ],             / "D" /
     [ [8, h'6e0e0494c6aa9f9072c3410304aab730', "E"], hash<<d1>>, hash<<M>> ]  / "E" /
   ]

                        Figure 15: Disclosure Proof

   If the Holder presents all the non-Decoy entries A to E of Figure 11
   instead, every copath node of A, B, C, and D is visited: their Merkle
   proofs each contain only their Redacted Entry.  The Merkle proof of E
   is unchanged and contains hash<<d1>> and hash<<M>>.  The resulting
   Disclosure Proof contains 2 hashes.

   If the Holder presents only A and B, the Merkle proof of A contains
   hash<<K>> and hash<<S>>, which are then visited, so the Merkle proof
   of B contains no hash.

6.  Verification

   An SMD-CWT Verifier MUST perform the same verification as an SD-CWT
   Verifier.  This section only describes how to validate a Disclosure
   Proof against the redacted_root_hash of the corresponding container.

   To validate an SMD-KBT, repeat this verification for all the
   disclosures presented.  Then also perform the validation described in
   Section 9 of [SD-CWT] since they all should pass as well.

   In this section, n is the size encoded in the redacted_root_hash (the
   first element of the array); the Merkle tree therefore has 2^n
   leaves, its node indexes range from 0 to 2^ (n+1) - 2, and its root
   has node index 2^n - 1.

   The Verifier proceeds as follows:

   1.  Verify that the Disclosure Proof contains at least one and at
       most 2^n Merkle proofs.

   2.  For each Merkle proof:

       1.  Verify that it contains at most n + 1 elements.

       2.  Verify that its first element is a Redacted Entry, and that
           the node index of this Redacted Entry is the node index of a
           leaf, i.e., an even number less than or equal to 2^ (n+1) -
           2.

       3.  Verify that this Redacted Entry matches the type of the
           container: a salted-merkle-claim if the container is a map,
           or a salted-merkle-element if it is an array, as defined in
           Figure 9.  In particular, a Redacted Entry of a Decoy, which
           only contains a salt, is rejected.

   3.  Verify that the node indexes of the Redacted Entries are sorted
       in increasing order.

   4.  Initialize a visited set with the node indexes of the presented
       leaves and of all their ancestors.  Also maintain a table
       associating node indexes with hashes, initially empty.

   5.  For each Merkle proof:

       1.  Remove the node index from the Redacted Entry.  The remaining
           array is an SMD-CWT entry: compute its hash as described in
           Section 4.3 and record it for the leaf in the table.

       2.  Walk the copath of the leaf, from the leaf up to the root.
           For each node of the copath:

           1.  If this node is in the visited set, skip it.

           2.  Otherwise, take the next hash of the Merkle proof, record
               it for that node in the table, and add the node to the
               visited set.  If the Merkle proof has no hash left, the
               validation fails.

       3.  Verify that all the hashes of the Merkle proof have been
           consumed.  If not, the validation fails.

   6.  Compute the hash of the root by walking down the tree from the
       root.  For each node reached:

       1.  If the table records a hash for this node, this is its hash,
           and its subtree is not walked.

       2.  Otherwise, if this node is a leaf, the validation fails.

       3.  Otherwise, walk its left child and then its right child.  Its
           hash is the hash of the concatenation of their hashes, the
           hash of the left child coming first.

   7.  Verify that the hash of the root is equal to the root hash in the
       redacted_root_hash.

   8.  If any of these verifications fails, the validation of the whole
       Disclosure Proof fails.

   Applied to the Disclosure Proof of Figure 15, the visited set
   initially contains nodes 0, 1, 3, 5, 6, 7, 8, 9, and 11.  The
   Verifier then:

   1.  Processes the Merkle proof of A: it records hash<<A>> for node 0
       and hash<<B>> for node 2.  Nodes 5 and 11 are visited.

   2.  Processes the Merkle proof of D: it records hash<<D>> for node 6
       and hash<<C>> for node 4.  Nodes 1 and 11 are visited.

   3.  Processes the Merkle proof of E: it records hash<<E>> for node 8,
       hash<<d1>> for node 10, and hash<<M>> for node 13.  Node 3 is
       visited.

   4.  Computes the hash of the root.  The visited set now contains
       nodes 0 to 11 and 13, and the table associates nodes with hashes
       [(0, A), (2, B), (4, C), (6, D), (8, E), (10, d1), (13, M)].  The
       root V (node 7) is not in the table, so the Verifier walks down
       to R (node 3) and S (node 11), which are not in the table either.
       Under R, J (node 1) and K (node 5) are computed from nodes 0 and
       2, and 4 and 6.  Under S, L (node 9) is computed from nodes 8 and
       10, and M (node 13) is in the table.  R is then computed from J
       and K, S from L and M, and V from R and S.

   5.  Verifies that hash<<V>> is equal to the root hash in the
       redacted_root_hash.

7.  Benefits over SD-CWT

7.1.  Smaller Tokens

   In SD-CWT, the payload contains the hash of every redacted entry,
   disclosed or not: a container with e redacted entries costs 34 * e
   bytes in every presentation (assuming sd_alg is SHA-256).

   The size of a presentation therefore grows linearly with e in SD-CWT,
   but only logarithmically in SMD-CWT.  For instance, the Disclosure
   Proof of Figure 15 contains 4 hashes in addition to the root hash,
   i.e., 34 * 5 = 170 bytes, whereas an SD-CWT with the same 5 entries
   and 2 Decoys contains 34 * 7 = 238 bytes of hashes.

7.2.  Privacy

   In SD-CWT, the payload contains one hash per redacted entry, so a
   Verifier learns the number of redacted entries of each container Also
   given presentation of SD-KBT are linkable, a Verifier can witness an
   array of redacted elements grow or shrink which degrades privacy of
   the Holder.  Decoys can be used to mitigate that, but they are
   expensive in terms of space wasted.

   In SMD-CWT, the Verifier only learns the logarithmic size of the
   tree.  The Issuer can choose a larger n to hide this number further,
   at the cost of at most one hash per additional level (see
   Section 7.3).

7.3.  Free Decoys

   In SD-CWT, each Decoy adds one hash, i.e., 34 bytes, to the presented
   token.

   In SMD-CWT, the presented token contains only the root hash and the
   Merkle proofs of the disclosed claims.  The size of these proofs
   depends on the height of the tree, not on the number of its leaves.
   Decoys can therefore be added at no cost up to the next power of two.
   Beyond that, doubling the number of leaves adds one level to the
   tree, which costs at most one additional hash, i.e., 34 bytes: the
   subtree rooted at the new copath node contains no presented leaf, and
   its hash is included at most once in the Disclosure Proof (see
   Section 5).

   ; in SMD-CWT
   salted-merkle-array = [ +bstr-encoded-salted-merkle-entry ]
   bstr-encoded-salted-merkle-entry = bstr .cbor salted-merkle-entries

   ; in SMD-KBT
   salted-array-proofs = [ +bstr-encoded-salted-proof ]
   bstr-encoded-salted-proof = bstr .cbor disclosure-proof

   ; where salted-claim, salted-element and decoy are already defined in {{SD-CWT}}
   salted-merkle-entry = salted-claim / salted-element / decoy

   salted-merkle-entries = [ +salted-merkle-entry ]

   ; one Merkle proof per presented leaf, ordered by increasing node index
   disclosure-proof = [ +merkle-proof ]

   merkle-proof = [
     redacted-entry,
     * bstr             ; hash of a copath node, from the leaf up to the root
   ]

   ; a presented entry prefixed with the node index of its leaf; Decoys are never presented
   redacted-entry = salted-merkle-claim / salted-merkle-element
   salted-merkle-claim = [
     uint,              ; node index of the leaf
     bstr .size 16,     ; 128-bit salt
     any,               ; Claim Value
     (int / text)       ; Claim Key
   ]
   salted-merkle-element = [
     uint,              ; node index of the leaf
     bstr .size 16,     ; 128-bit salt
     any                ; Claim Value
   ]

   ; repeated here
   salted-claim = [
     bstr .size 16,     ; 128-bit salt
     any,               ; Claim Value
     (int / text)       ; Claim Key
   ]
   salted-element = [
     bstr .size 16,     ; 128-bit salt
     any                ; Claim Value
   ]
   decoy = [
     bstr .size 16      ; 128-bit salt
   ]

   ; redacted_claims_root is used as a map label. The corresponding value is

   redacted_root_hash = [
     uint  ; logarithm(2) of the number of leaves represented in this root hash
     bstr, ; root hash
   ]
